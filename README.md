# ft_traceroute

`ft_traceroute` is a small traceroute implementation written in C.
It discovers the route to a destination by sending probes with an increasing IP **TTL (Time To Live)** value and reading the **ICMP messages** generated by routers and by the destination host.

The program supports two probe modes:

- **UDP mode (default):** sends UDP datagrams to high-numbered destination ports.
- **ICMP mode (`-I`):** sends ICMP Echo Requests, similar to `ping`.

The implementation processes probes **sequentially**: one probe is sent, its reply is waited for (or it times out), and only then is the next probe sent.

---

## 1. Main Data Structures

The program uses both system networking structures and a few project-specific structures.

### `struct sockaddr_in`

`struct sockaddr_in` describes an IPv4 socket address.

```c
struct sockaddr_in {
    short             sin_family;
    unsigned short    sin_port;
    struct in_addr    sin_addr;
    char              sin_zero[8];
};
```

The important fields for this project are:

- `sin_family`: address family, `AF_INET` for IPv4.
- `sin_port`: UDP port number. Port values are stored in **network byte order**, so the program uses `htons()` when necessary.
- `sin_addr`: the IPv4 address, stored as a `struct in_addr`.
- `sin_zero`: padding used to keep the structure aligned.

For example, the destination address resolved from `google.com` is stored in `p->dest`.

### `struct in_addr`

`struct in_addr` represents an IPv4 address.

The actual address is stored in:

```c
struct in_addr {
    in_addr_t s_addr;
};
```

The program compares addresses using `s_addr` and converts them to printable form with `inet_ntop()`.

For example:

```c
if (oip->ip_dst.s_addr != p->dest.sin_addr.s_addr)
    return (0);
```

This checks whether the packet contains our destination IP address.

### `struct ip`

`struct ip` represents the **IPv4 header** of a received packet.

The field used most importantly by this project is:

```c
ip->ip_hl
```

`ip_hl` is the IP header length in 32-bit words. Therefore, the actual header size in bytes is:

```c
size_t hlen = (size_t)ip->ip_hl << 2;
```

The normal IPv4 header is 20 bytes, but it can be larger if IP options are present. We therefore do **not** assume that the ICMP header always starts at `buf + 20`.

The program also uses:

- `ip->ip_src`: source address of the received packet.
- `ip->ip_dst`: destination address.
- `ip->ip_p`: encapsulated protocol, for example `IPPROTO_UDP` or `IPPROTO_ICMP`.

### `struct icmp`

`struct icmp` represents the **ICMP header**.

The fields relevant to this project are:

```c
icmp_type
icmp_code
icmp_id
icmp_seq
icmp_cksum
```

Their purpose depends on the ICMP message:

- `icmp_type`: identifies the ICMP message type, such as `ICMP_TIMXCEED`, `ICMP_UNREACH`, or `ICMP_ECHOREPLY`.
- `icmp_code`: gives more specific information about the message.
- `icmp_id`: identifies an ICMP Echo exchange.
- `icmp_seq`: identifies a particular Echo Request.
- `icmp_cksum`: checksum used to validate the ICMP message.

In ICMP mode, the program creates an Echo Request containing its own `id` and a sequence number.

### `t_reply`

`t_reply` stores the useful result of one received reply.

```c
typedef struct s_reply
{
    struct in_addr from;
    double          rtt;
    int             done;
} t_reply;
```

- `from`: address of the host that generated the reply.
- `rtt`: round-trip time in milliseconds.
- `done`: set to `1` when the reply proves that the final destination has been reached.

### `t_probe`

`t_probe` represents one probe packet and its result.

```c
typedef struct s_probe
{
    int         seq;
    int         sent;
    int         got;
    struct timeval send_time;
    t_reply     reply;
} t_probe;
```

- `seq`: sequence value used to identify the probe.
- `sent`: whether the probe was successfully sent.
- `got`: `1` for a received reply, `-1` for a timeout/send failure, `0` while waiting.
- `send_time`: timestamp taken immediately before sending the probe.
- `reply`: source address, RTT, and destination status.

### `t_hop`

`t_hop` groups all probes belonging to the same TTL value.

```c
typedef struct s_hop
{
    int     ttl;
    t_probe probes[3];
    int     done;
} t_hop;
```

By default, the program sends **3 probes per hop**.

`done` indicates that the final destination answered during this hop.

### `t_trace`

`t_trace` contains the global state of the traceroute process.

```c
typedef struct s_trace
{
    const char      *host;
    char             ip_str[INET_ADDRSTRLEN];
    struct sockaddr_in dest;
    int              send_sock;
    int              recv_sock;
    int              max_hops;
    int              nprobes;
    int              first_ttl;
    int              base_port;
    int              mode;
    unsigned short   id;
} t_trace;
```

The most important fields are:

- `host`: hostname entered on the command line.
- `ip_str`: printable IPv4 destination address.
- `dest`: resolved destination socket address.
- `send_sock`: UDP socket used in normal UDP mode.
- `recv_sock`: raw ICMP socket used to receive ICMP replies. In ICMP mode it also carries the Echo Requests.
- `max_hops`: maximum TTL value to test.
- `nprobes`: number of probes sent for each hop.
- `first_ttl`: initial TTL.
- `base_port`: starting UDP destination port.
- `mode`: `MODE_UDP` or `MODE_ICMP`.
- `id`: process identifier used to recognize our ICMP probes.

## 2. How Traceroute Works

The central idea of traceroute is to use the **IP TTL field** to make routers reveal the path step by step.

Every IPv4 packet contains a TTL value. Each router that forwards the packet decreases the TTL by one. If the TTL reaches zero, the router does not forward the packet. Instead, it normally sends an **ICMP Time Exceeded** message back to the sender.

This makes it possible to discover the route:

```text
TTL = 1  -> first router responds
TTL = 2  -> second router responds
TTL = 3  -> third router responds
...
TTL = N  -> destination responds
```

The program starts with `first_ttl` (normally `1`) and increments the TTL after each hop until:

1. the destination is reached, or
2. `max_hops` is reached.

### One hop in this implementation

For each TTL value, the program performs the following steps:

```text
Set IP_TTL
   |
   v
Send probe #1
   |
   v
Wait for matching ICMP reply / timeout
   |
   v
Calculate RTT and print result
   |
   v
Send probe #2
   |
   v
Wait for matching ICMP reply / timeout
   |
   v
Calculate RTT and print result
   |
   v
Send probe #3
   |
   v
Wait for matching ICMP reply / timeout
   |
   v
Print the hop and move to the next TTL
```

A timeout is displayed as:

```text
*
```

The program waits up to `PROBE_TIMEOUT` seconds for each individual probe.

## 3. How the Probe Is Sent

### UDP mode

In the default mode, the program sends a UDP datagram containing a 32-byte payload to the destination.

The destination port is derived from the probe sequence:

```c
dst.sin_port = htons(p->base_port + seq);
```

The important point is that the destination port gives us a way to identify which probe generated an ICMP error later.

For example:

```text
base_port = 33434

probe seq 0 -> UDP port 33434
probe seq 1 -> UDP port 33435
probe seq 2 -> UDP port 33436
```

### ICMP mode (`-I`)

In ICMP mode, the program sends an ICMP Echo Request directly.

It fills the ICMP header with:

```c
icmp_type = ICMP_ECHO
icmp_code = 0
icmp_id   = p->id
icmp_seq  = seq
```

The ICMP checksum is then calculated over the whole ICMP packet before sending it.

The pair `(id, seq)` identifies our Echo Request.

---

## 4. Why We Use Two Sockets

The implementation uses two different sockets in UDP mode:

```text
send_sock -> sends UDP probes
recv_sock -> receives ICMP messages
```

The receive socket is a **raw ICMP socket**:

```c
socket(AF_INET, SOCK_RAW, IPPROTO_ICMP)
```

Routers do not answer our UDP probes with UDP packets. Instead, when the TTL expires, they send ICMP messages back to us. The raw socket allows the program to inspect those ICMP packets directly.

In ICMP mode, the raw ICMP socket is used both to send Echo Requests and to receive Echo Replies / Time Exceeded messages.

---

## 5. Raw Socket Packet Parsing

When data is received from the raw ICMP socket, `buf` points to the **beginning of the outer IPv4 packet**.

The general layout is:

```text
buf
 |
 v
+--------------------------+
| Outer IP Header          |
| normally 20 bytes        |
+--------------------------+
| ICMP Header              |
| 8 bytes                  |
+--------------------------+
| ICMP Payload             |
|                          |
| original packet ...      |
+--------------------------+
```

The ICMP header does **not** necessarily start at `buf + 20`, because the outer IP header may contain options.

Therefore the program first calculates:

```c
hlen = (size_t)ip->ip_hl << 2;
```

and then:

```c
icmp = (struct icmp *)(buf + hlen);
```

This is the first important parsing step.

---

## 6. Understanding an ICMP Time Exceeded Packet

When an intermediate router drops our packet because the TTL reached zero, it sends an ICMP **Time Exceeded** message.

That ICMP message contains part of the original packet that caused the error. In our implementation, we use that embedded information to identify our own probe.

The structure is approximately:

```text
Outer IP Header
        |
        v
+--------------------------+
| Outer IP Header          |
+--------------------------+
| ICMP Time Exceeded       |
| type = 11                |
+--------------------------+
| Original IP Header       |
| of our probe              |
+--------------------------+
| Original transport hdr   |
| UDP or ICMP               |
+--------------------------+
```

The program first checks the outer IP header, then reads the outer ICMP header.

For example:

```c
if (icmp->icmp_type != ICMP_TIMXCEED ...)
    return (0);
```

After the outer ICMP header, it locates the **original IP header**:

```c
oip = (struct ip *)(buf + hlen + ICMP_MINLEN);
```

Again, the original IP header length is read from `oip->ip_hl` rather than assuming 20 bytes:

```c
oh_len = (size_t)oip->ip_hl << 2;
```

---

## 7. How UDP Replies Are Identified

In UDP mode, an intermediate router normally returns an ICMP Time Exceeded message.

The original UDP packet is embedded inside that ICMP message. We use the embedded UDP destination port to identify our probe.

The parsing becomes:

```text
Outer IP
   |
   +--> Outer ICMP Time Exceeded
             |
             +--> Original IP
                    |
                    +--> Original UDP
```

The program checks three important things:

### 1. The embedded packet is actually UDP

```c
if (oip->ip_p != IPPROTO_UDP)
    return (0);
```

### 2. The embedded destination is our target

```c
if (oip->ip_dst.s_addr != p->dest.sin_addr.s_addr)
    return (0);
```

### 3. The embedded UDP destination port matches the probe

The UDP destination port is read from the embedded UDP header and compared with:

```c
p->base_port + seq
```

This prevents unrelated ICMP packets from being mistaken for our probe's reply.

### Reaching the final destination in UDP mode

When the UDP packet reaches the destination, the destination port is normally not listening.
The destination can therefore return an ICMP **Destination Unreachable / Port Unreachable** message.

The program considers the destination reached only when:

```text
ICMP type  = Destination Unreachable
ICMP code  = Port Unreachable
source IP  = destination IP
```

This is how UDP traceroute distinguishes the final host from an intermediate router.

---

## 8. How ICMP Replies Are Identified

ICMP mode uses a slightly different packet structure.

### Destination reply

When the probe reaches the destination, the destination sends an ICMP Echo Reply directly:

```text
Outer IP Header
        |
        v
+--------------------------+
| ICMP Echo Reply          |
+--------------------------+
| id + sequence            |
+--------------------------+
```

The program checks:

```c
icmp->icmp_type == ICMP_ECHOREPLY
ntohs(icmp->icmp_id) == p->id
ntohs(icmp->icmp_seq) == seq
```

If all of these match, the reply belongs to our probe and the destination has been reached.

### Intermediate router reply

For an intermediate router, the message is an ICMP Time Exceeded packet.
The router includes the original IP packet and the beginning of the original ICMP Echo Request.

So the program parses:

```text
Outer IP
   |
   +--> ICMP Time Exceeded
             |
             +--> Original IP
                    |
                    +--> Original ICMP Echo Request
                               |
                               +--> id + seq
```

The original ICMP `id` and `seq` are then compared with the values of the probe that is currently being waited for.

This is important because the raw socket can receive ICMP packets that were not generated by the current probe.

---

## 9. Matching a Reply to a Probe

The `wait_for_reply()` function waits for packets using `select()`.

The basic logic is:

```text
send probe
   |
   v
start timer
   |
   v
select() waits until the raw socket is readable
   |
   +--> packet received
   |       |
   |       v
   |   parse packet
   |       |
   |       v
   |   does it match our probe?
   |       |
   |      yes --> calculate RTT / return
   |       |
   |      no  --> ignore and keep waiting
   |
   +--> timeout --> print '*'
```

A packet is accepted only if its identifying information matches the probe currently being processed.

This is especially important with a raw socket because the socket may receive ICMP traffic unrelated to this traceroute instance.

---

## 10. RTT Measurement

Before sending a probe, the program stores the current time:

```c
gettimeofday(&pr->send_time, NULL);
```

When the matching reply is received, it reads the current time again.
The difference is converted into milliseconds:

```text
RTT = receive_time - send_time
```

For example:

```text
probe sent     : 14:20:10.123456
reply received : 14:20:10.133164

RTT            : 9.708 ms
```

The RTT is then printed for that probe.

---

## 11. Summary of the Complete Flow

The complete traceroute process can be simplified to:

```text
Resolve hostname
      |
      v
Open sockets
      |
      v
TTL = 1
      |
      v
Set IP_TTL on the probe socket
      |
      v
Send one probe
      |
      v
Wait for one matching ICMP reply
      |
      +--------------------+
      |                    |
   Time Exceeded       Destination reached
      |                    |
      v                    v
Print router + RTT      Print destination + RTT
      |                    |
      +----------+---------+
                 |
                 v
       Send remaining probes
       for the current TTL
                 |
                 v
          Next TTL value
                 |
                 v
             TTL += 1
                 |
                 v
       Stop at destination
       or maximum hop count
```

The most important concept is that **the probe itself is not the reply**. The traceroute process works by sending a packet with a controlled TTL and then interpreting the ICMP message that comes back. The contents of that ICMP message allow the program to determine **which router answered, which probe it corresponds to, whether the destination was reached, and how long the round trip took**.
